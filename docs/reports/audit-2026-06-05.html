🟡 Important — Backend Issues

  • Important Panic in hot path (every login) — internal/api/handlers/auth.go:203: generateCSRFToken() panics on crypto/rand.Read failure. Should return (string, error) and propagate.
  • Important Panic on missing query key (mid-request) — internal/database/query_registry.go:59: Get() panics on missing key. Should validate all required keys in BuildQueryRegistry at startup — fail fast at boot, not mid-request.
  • Important dispatch_service.Create() bypasses repo abstraction — internal/service/dispatch_service.go:86-116: issues raw tx.ExecContext with literal INSERT instead of calling s.dispatches.Create(). Duplicates queries.yaml entry, breaks testability.
  • Important escalation_service.ruleApplies() logic stub disguised as real code — internal/service/escalation_service.go:71: ignores dispatch argument entirely; always returns rule.IsActive. All active rules fire on all overdue dispatches regardless of type, urgency, or conditions.
  • Important Inline SQL in auth-critical repos — internal/database/repos/user_repo.go, session_repo.go, password_reset_repo.go: all use inline SQL strings. The inline GetByEmail does NOT scope by organization_id (YAML version does: WHERE organization_id = $1 AND email_address = $2 AND is_active = true) — behavioral gap.
  • Important Expired session regression — session_repo.go::GetByTokenHash inline SQL does NOT filter WHERE expires_at > now(). YAML definition session.get_session_by_token_hash includes this filter. Expired sessions may be considered valid by auth middleware.
  • Important No input validation on CreateUser role — internal/api/handlers/admin.go:53-60: no validation on role value or email format. Invalid role → cryptic Postgres enum violation instead of 400. Also: any ADMIN can create a SYS_ADMIN account via this endpoint.
  • Important No MaxBytesReader on any handler — JSON body DoS possible on all endpoints. Add http.MaxBytesReader(w, r.Body, 1<<20) in middleware.
  • Important No PostgreSQL service in CI test-backend job — .github/workflows/ci.yml: integration tests in internal/integration/ require a real DB; they skip/fail without services: postgres: block. Add a postgres service container.
  • Important CD workflow: no migration step before kubectl set image — .github/workflows/cd.yml: schema changes break new pods until manually migrated. k8s-rollout.sh handles this correctly but is not called by the CD workflow.
  • Important Zero ARIA attributes on interactive elements (Frontend) — auth/login.vue:85, dashboard.vue:139-151, WorkspaceSidebar.vue:103 & 226, admin/navigation.vue:186: bare <button> elements with no accessible names. WCAG 2.1 AA blocker.
  • Important Password reset accepts any-length password — internal/service/auth_service.go:208-226: ConfirmPasswordReset has no minimum password length validation. Bootstrap path enforces 12-char minimum; reset path does not.
  • Important RBAC rejection not logged to audit ledger — internal/rbac/middleware.go:55-78: PERMISSION_DENIED and RBAC_ELEVATION_ATTEMPT events not written on 403 rejection. Sprint 1 definition of done requires this.
  • Important useRuntimeConfig.refresh() is a stub — composables/useRuntimeConfig.ts:176-181: refresh() is a 300ms setTimeout, never calls real GET /api/v1/config. Must wire to real API once backend is live. Shape already matches API contract.

Expert Commentary

🎨 Frontend Design Assessment — Agent 1

The Aethel frontend is a high-quality, production-credible UI prototype demonstrating disciplined component reuse and a mature design system. The three-layer CSS variable architecture is correctly implemented, the semantic token migration was thorough, and the auth layer (useAuth.ts + fetch.ts + auth.client.ts) is production-grade — significantly above expectations for a Phase 1 prototype. The primary weakness is accessibility: zero ARIA attributes on custom interactive elements is a hard WCAG 2.1 AA failure. The reports.vue chart stubs present a slightly unfinished impression. For Phase 2, the most critical wiring task is connecting useRuntimeConfig.refresh() to the real GET /api/v1/config endpoint — the shape already matches the API contract exactly. — Agent 1 · Frontend Auditor · 2026-06-05

⚙️ Go Backend Architecture Assessment — Agent 2

The architecture is genuinely production-quality for a sprint project. Security fundamentals are correct throughout: Argon2id passwords, HMAC-signed JWTs (no org claim needed), atomic refresh token rotation, CSRF double-submit cookies with crypto/subtle.ConstantTimeCompare, and layered rate limiting. The audit ledger with SHA-256 checksum chaining is correctly implemented with matching hash formulas in both workflow_service.go and green_note_repo.go. The main technical debt is the split SQL discipline: auth-critical repos (user_repo, session_repo, password_reset_repo) predate the QueryRegistry pattern and were never migrated. Combined with dispatch_service.Create() bypassing its own repo abstraction to write SQL inline in a transaction, the codebase has an inconsistent SQL management story that will complicate future auditing. — Agent 2 · Go Backend Auditor · 2026-06-05

🔒 Security Assessment — Agent 4

The Aethel backend demonstrates sophisticated security thinking — Argon2id is correct and complete, session rotation is properly atomic, and the CSRF double-submit pattern is implemented precisely including ConstantTimeCompare. The RBAC system correctly isolates admin.audit to SYS_ADMIN only. However, four high/medium findings reduce the posture: the absence of a CSP header combined with unguarded v-html in BlockRichText creates a viable stored XSS path, the CreateUser endpoint allows privilege escalation by any admin, the password reset flow accepts single-character passwords, and the fallback JWT secret is a production time bomb. The hardcoded fallback secret should be replaced with a hard startup failure. — Agent 4 · Security Auditor · 2026-06-05
